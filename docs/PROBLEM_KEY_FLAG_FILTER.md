# 문제저장소 "주요 문항" 표시 · 복합 필터

브랜치 `feature/problem-key-flag-filter`(main `bcf1a21b` 기준). **병합·배포·운영 Firebase 쓰기 없음.** 아래 "검증"은 모두 메모리 Firestore 가짜 + 합성 문제로 한 것이며 운영 데이터 동작은 확인하지 않았다.

## 데이터 (problems/{문제ID} 문서, 선택 필드)
| 필드 | 의미 | 값이 없을 때 |
|---|---|---|
| `isKeyProblem` (boolean) | ★ 주요 문항 | 일반 문항 |
| `keyProblemUpdatedAt` (ISO 문자열) | 마지막 표시/해제 시각 | — |
| `isPastExam` (boolean) | 기출 (**현재 코드·데이터 어디에도 없음**, 필터만 준비) | 기출 아님(임의로 기출 처리하지 않음) |

표시·해제는 `doc(문제ID).update({isKeyProblem, keyProblemUpdatedAt})` **두 필드만** 부분 업데이트한다. 문서가 없으면 만들지 않고 실패로 표시한다(기존 `problemUpdateDoc`은 없으면 만드는 동작이라 쓰지 않음). 문제 이미지·정답키(`problemKeys`)·풀이·출처·학생 기록·과제 기록은 건드리지 않는다. 화면 값은 저장이 성공한 뒤에만 바뀌고, 저장 중에는 그 문제의 버튼이 잠기며(연속 클릭 무시), 성공/실패 문구가 그 문제 옆에 남는다.

## 필터 동작
- 조건(검색어·학년·학기·대단원·중단원·핵심개념·도형구조·묻는 것·풀이기술·★주요 문항·기출)은 **모두 만족하는 문제만**(교집합) 보인다(`problemMatches`).
- Firestore 한 질의에는 `array-contains`를 하나만 쓸 수 있으므로 서버 조회 조건은 하나만 고른다(`problemServerQuery`): 주요 문항 → 기출 → 기존 검색 토큰 순. 주요 문항·기출은 **단일 필드 `==` 질의**라 복합 색인이 필요 없다(`firestore.indexes.json` 변경 없음). 나머지 조건은 가져온 문서마다 모두 확인한다.
- 기존에는 60개 한 페이지만 읽고 화면에서 걸러서 "현재 불러온 범위"만 검색됐다. 이제는 조건에 맞는 문제가 한 페이지(60개) 더 모일 때까지(또는 저장소 끝까지, 한 번에 최대 10 페이지) 서버 페이지를 이어 읽는다. **검사 한계:** 한 번 누를 때 최대 10페이지(600개)까지만 읽는다. 끝까지 못 읽었으면 "저장소 일부만 검사한 결과예요(N개 검사, 한 번에 최대 600개까지)"와 "조건에 맞는 문제 더 찾기" 버튼으로 이어서 검사하라고 표시하고, 저장소 끝까지 읽은 뒤에만 "저장소 끝까지 검사했어요(N개 검사)"라고 표시한다(1300개 시험으로 확인: 3번 눌러 끝까지 검사). 서버 검색이 실패해 일반 목록으로 대체되면 "전체 검색이 아니에요 … 새로고침으로 다시 시도"를 표시한다.
- 필터 변경이 읽기 중에 겹치면 마지막 선택이 최종 결과가 된다.
- **정렬:** 기존 화면에 정렬 기능이 없어 새로 만들지 않았다. 표시 순서는 저장소(문서 ID) 순서이며 필터를 켜도 유지된다.
- 페이지 처리는 기존처럼 "더 불러오기"(번호 페이지 아님) 방식을 유지했다.

## 한계·미확인
- **운영 Firestore 보안 규칙(미확인)**: 이 브랜치(main 기준)에는 규칙 파일이 없고, 이 작업 환경에는 Firebase/Google 로그인 정보가 없어 배포된 규칙을 직접 조회할 수 없다. 다른 브랜치(`security/rules-plan-emulator-tests`)의 `security/firestore.rules.current`는 "2026-10-19 Firebase 콘솔 규칙 탭에서 원장이 직접 확인한 현재 배포 규칙(2026-08-19 게시)"이라고 적힌 **기록**이며 내용은 `request.auth != null` 이면 모든 문서 읽기·쓰기 허용이다. 이 기록이 맞고 이후 바뀌지 않았다면 교사 세션의 `problems` 부분 업데이트는 허용되지만(**동시에 학생 세션도 같은 쓰기가 가능한 기존 노출이 있다** — 표시 버튼은 교사 화면에만 있고 학생 화면에는 없다), 오늘 시점의 실제 규칙인지는 확인하지 못했다. 막혀 있으면 화면에 "저장 실패 · permission-denied …"로 표시된다. 규칙은 바꾸지 않았다. 필요하면 `problems`의 `isKeyProblem`·`keyProblemUpdatedAt` 두 필드만 교사 계정이 갱신할 수 있게 좁게 허용하는 안을 따로 검토해야 한다.
- 단일 필드 색인은 기본 자동 생성이지만 운영 프로젝트에서 예외로 꺼져 있는지는 확인하지 못했다(꺼져 있으면 서버 검색 실패 → "전체 검색 아님" 표시).
- `searchTokens`가 없는 옛 문제는 기존 토큰 검색(학년·단원 등 텍스트 조건 단독)에서 서버가 못 찾는 기존 한계가 그대로다. 주요 문항·기출 필터는 토큰을 쓰지 않아 영향이 없다.
- **"새 풀이 등록 데스크"의 주요 문항 저장**: 이 저장소(main 및 모든 원격 브랜치)에서 해당 코드·필드를 찾지 못했다. 학원앱 문제와 어떤 ID로 연결되는지는 **확인할 수 없어 연결하지 않았다.** 풀이 자료(`solutionPhotos`)·질문 사진에는 표시를 붙이지 않았다(문제 ID가 없는 자료에 임의 표시 금지). 데스크가 별도 저장소·프로젝트라면 그 코드와 저장 필드(문제 ID 포함)를 알려 주셔야 연결 방식을 정할 수 있다.
- **기출**: 현재 분류 데이터가 없다. 필터는 `isPastExam===true` 문서만 보여 주며, 데이터가 없으면 0건과 안내 문구를 표시한다. 적용 방안: ① 기출 출처(학교·연도·학기·시험 종류)를 담을 필드 설계 → ② PDF 수집 때 출처명·파일명으로 후보를 만들고 교사가 확인 → ③ 확정된 문서에만 `isPastExam:true`(+`examSchool`·`examYear`) 부분 업데이트. 파일명 규칙이나 기출 목록 자료가 필요하다.
- 같은 영역을 만지는 PR #14(draft)와는 함수 수준에서 겹치지 않는다(`problemFilteredItems`·`loadProblemPage`·`renderProblemRepository`를 PR #14가 바꾸지 않음).
