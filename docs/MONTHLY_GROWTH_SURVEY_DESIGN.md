# 월간 성장 설문 — 보안·부하 제한 설계

상태: 구현 전 설계 기준. 이 문서는 운영 코드나 데이터베이스를 변경하지 않는다.

## 목적

매월 20일 학생이 학습을 돌아보고, 원장이 같은 문항에 관찰 평가와 학생 메모·학부모 메모를 더한다. 학생은 게시된 결과와 학생 메모를 로그인 메인보드에서 보고, 원장은 한 화면에 전체 문항·양쪽 응답·학생 목표·교사 지원 약속·학부모 메모가 보이는 공유용 보고서를 캡처한다.

## 부하 제한 원칙

주말학습에서 문제가 됐던 로그인 시 전체 `assignments` 컬렉션 로드 패턴을 재사용하지 않는다.

- 학생 로그인 시 설문 컬렉션을 읽지 않는다.
- 월간 예약 작업이나 전 학생 대상 설문 생성 작업을 만들지 않는다. 활성 기간은 한국시간 기준 날짜로 계산한다.
- 학생이 메인보드의 설문 영역을 열 때만 본인과 해당 월 조합의 문서 ID를 정확히 조회한다. 조회량은 0~1건이다.
- 학생은 설문 문서에 실시간 리스너를 붙이지 않는다. 화면 진입 시 1회 조회하고, 제출 시 1회 저장한다.
- 원장은 학생 한 명의 설문을 열 때 정확 조회 1건을 사용한다.
- 원장 월별 목록은 `month == YYYY-MM` 조건으로 최대 10건씩 페이지 조회한다. 다음 페이지를 누를 때만 이어 읽으며 전체 설문 이력을 한꺼번에 읽지 않는다.
- 추천 초안은 현재 원장 편집 화면에서 선택한 학생의 해당 월 `monthlyReports/{YYYY-MM}_{studentId}` 문서 1건만 참고한다. 해당 자료가 없으면 기본 문항 초안을 제시한다. 학원 전체 원자료를 스캔해 추천하지 않는다.
- 문항표·척도는 정적 템플릿으로 둔다. 문항 템플릿을 학생별로 복제하지 않는다.
- 문서에는 점수와 짧은 메모만 저장한다. 사진과 원본 학습 기록을 복제하지 않는다.

## 문서 구조 초안

컬렉션: `growthSurveys`

문서 ID: `{studentId}_{YYYY-MM}`  
예: `stu_ab12cd34_2026-10`

문서 하나에 그 학생의 한 달 설문만 저장한다. 18개 안팎 문항은 배열로 저장한다.

```json
{
  "studentId": "stu_ab12cd34",
  "month": "2026-10",
  "status": "open",
  "templateVersion": 1,
  "student": {
    "ratings": { "routine_01": 4, "concept_02": 3 },
    "reflection": "이번 달에 꾸준히 한 것",
    "smallGoal": "수업이 끝난 날 오답 1개를 다시 풀기",
    "submittedAt": null
  },
  "teacher": {
    "ratings": { "routine_01": 3, "concept_02": 4 },
    "studentMemo": "",
    "supportCommitment": "",
    "parentMemo": ""
  },
  "evidenceRefs": [],
  "createdAt": null,
  "updatedAt": null,
  "publishedAt": null
}
```

점수는 학생·교사 응답을 각각 보존한다. 합산 총점이나 서열은 만들지 않는다. `evidenceRefs`에는 원자료를 복제하지 않고 필요할 때만 기존 기록을 가리키는 ID를 둔다. 학생에게는 공개된 보고서 내용만 보여준다.

## 권한 경계

- 학생 인증은 브라우저의 학생 목록 전체 다운로드와 코드 비교를 사용하지 않는다. 서버가 학생 코드를 확인하고 학생 ID가 담긴 Firebase custom token을 발급하는 기존 보안 2단계 설계와 맞춘다.
- 학생은 본인 ID와 해당 월이 일치하는 설문만 정확 조회할 수 있다. 다른 학생 ID로 요청하면 Firestore 규칙 또는 서버가 거부한다.
- 학생이 제출할 수 있는 것은 자기 응답 영역뿐이다. 교사 평가·메모·공개 상태는 학생 요청으로 변경할 수 없다.
- 교사 편집과 공개는 원장 인증으로만 허용한다.
- 부모용 화면은 인증 없는 공유 링크로 만들지 않는다. 원장이 로그인한 화면에서 전체 보고서를 한 페이지로 렌더링해 직접 캡처한다.
- 현재 운영 규칙은 모든 인증 세션에 넓은 권한을 주는 것으로 보안 계획에 기록돼 있다. 이 전제가 바뀌기 전에는 설문 응답을 운영 Firestore에 기록하거나 기능을 켜지 않는다.

## 월간 진행

1. 매월 20일 이후 학생 메인보드에 해당 월 설문 진입 영역을 표시한다. 달력 날짜 계산만으로 표시하며 예약 함수는 호출하지 않는다.
2. 학생이 열면 본인 문서 한 건을 조회한다. 문서가 없으면 화면에서 설문을 작성하고, 제출 때 고정 문서 ID로 생성한다.
3. 원장이 특정 학생 편집 화면을 열면 해당 학생·해당 월 문서와 해당 학생의 월말 리포트 초안만 조회한다. 추천 문항은 초깃값으로 채우고 원장이 수정한다.
4. 원장이 관찰 평가, 학생 메모, 교사 지원 약속, 학부모 메모를 작성한 뒤 게시한다.
5. 게시 후 학생 메인보드에는 학생 평가 옆에 교사 평가와 학생 메모, 다음 달의 작은 목표와 교사 지원 약속을 표시한다. 원장 화면에는 부모용 한 페이지 보고서를 함께 표시한다.

## 구현 전제·검증 항목

1. 학생별 인증을 서버에서 확정하는 기능과 Firestore 규칙이 먼저 준비돼야 한다. PR #12의 Phase 2는 설계·테스트 초안이며 운영 적용 상태가 아니다.
2. 설문 컬렉션의 학생 읽기/쓰기는 정확한 학생 ID와 월 문서에만 허용하고, 원장 이외의 목록 조회는 거부한다.
3. 에뮬레이터 시험은 학생 A 본인 조회·제출 허용, 학생 A의 학생 B 조회·변조 거부, 학생의 교사 필드 변경 거부, 미게시 결과 숨김, 원장 월별 목록 페이지 제한을 포함한다.
4. 운영 기능을 켜기 전 기존 로그인·주말학습·숙제 기능을 포함한 앱 전체가 새 인증/규칙과 호환되는지 별도로 확인한다.
5. 운영 규칙 게시·운영 데이터 변경·서비스 배포는 이 설계 문서와 별도 승인 대상이다.


## 현재 운영 코드와의 차이 — 선행 수정 필요

현재 `main`의 `initFirebase()`는 익명 인증 후 로그인 전부터 `attachCoreListeners()`를 호출한다. 이 함수는 `students`, `classes`, `courses`, `weekendClasses`를 전체 구독한다. 학생 코드는 브라우저에서 전체 학생 목록과 대조한다. 따라서 위 부하·권한 원칙은 현재 운영 코드의 설명이 아니라 목표 설계다.

성장 설문을 기존 화면에 연결하기 전에 다음 변경이 선행돼야 한다.

1. 학생 코드를 브라우저 전체 목록에서 비교하지 않고, 서버가 확인해 `studentId`가 들어간 인증 토큰을 발급한다.
2. 로그인 전에는 학생·반·설문 컬렉션 리스너를 시작하지 않는다.
3. 학생 로그인 후에는 본인 학생 문서와 소속 반 등 화면에 필요한 최소 기준정보만 조회한다. 원장 로그인 후에만 전체 명단을 조회한다.
4. 기존 넓은 Firestore 규칙을 학생별 권한 규칙으로 전환하고, 기존 앱의 주말학습·숙제·질문 등 필요한 조회가 모두 제한된 쿼리와 맞는지 확인한다.
5. 그 후 성장 설문 한 건 조회·제출을 통합한다.

이 선행 변경과 규칙이 확인되기 전에는 성장 설문 UI를 운영 학생 로그인에 노출하거나 응답을 운영 저장소에 쓰지 않는다. PR #25는 위 범위를 구현한 결과물이 아니라, 부하와 접근 권한의 승인 기준을 고정한 설계 draft다.
