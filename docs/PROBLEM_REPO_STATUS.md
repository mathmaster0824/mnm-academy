## 0. 서버 경로 조사 결과 (저장소·설정에서 확인한 범위)
- 사진/PDF 서버 주소는 앱 코드(`index.html`)에 고정돼 있다(`PHOTO_API_BASE`, Cloudflare Workers 주소). 호출 경로: `/upload`(문항 이미지·사진 저장), `/photo`(표시·삭제), `/segment-problem-page`(AI 페이지 분리), `/analyze-problem`(AI 문항 분석). 요청마다 로그인 토큰을 붙여 보낸다(토큰 값은 다루지 않음).
- **서버 소스·배포 설정(wrangler 등)은 이 저장소 어디에도 없다.** `functions/` 는 월말 보고 예약 작업 하나뿐이며 문제저장소와 무관하다. 앱 코드가 들어간 커밋(2026-10-17 "Add files via upload") 하나에 이 경로들이 함께 들어 있어 **서버가 이 경로들을 실제로 배포했는지는 저장소만으로 알 수 없다.**
- 운영 서버에 직접 호출해 확인하는 방법은 이 환경에서 승인되지 않아 시도하지 않았다. → "서버에 경로가 있는지"는 **확인되지 않음**.
- 따라서 원장님께 서버 코드를 요구하지 않고도 할 수 있는 확인: 아래 6번(앱에서 PDF 1건 올려 보기). 성공하면 `/upload` 가 살아 있는 것이고, 실패 메시지가 어느 경로가 없는지 알려 준다.

## 0-1. 요청 주소와 전송 데이터 (index.html 코드 근거)
**주소 결정:** 주소는 설정 파일·환경값 없이 코드에 고정된 상수 하나다 — `PHOTO_API_BASE = 'https://mnm-photo-api.jihagondu.workers.dev'` (index.html:1215). 각 호출은 끝의 `/`를 지운 뒤 경로를 붙인다: `/upload`(1247, 7164), `/photo?key=…`(1192, 1234), `/segment-problem-page`(1217→8114), `/analyze-problem`(1216→8430). 주소 소유자(Cloudflare 계정)는 코드로 확인되지 않음 → **미확인**.

| 호출 | 언제 | 본문에 들어가는 것 | 근거 |
|---|---|---|---|
| `POST /upload` (문항 이미지) | PDF 수집 중 문항마다 | 문항 영역을 그린 **JPEG 이미지**(확대 2배, 화질 .86), 파일명 `<PDF 파일명>_q<번호>.jpg`, `kind=problem-crop`, `category=problem-crop`, `studentId=problem-bank`(고정 문자열 — 학생 정보 아님) | 8324, 7156–7165, `problemPdfCropBlob` |
| `POST /upload` (페이지 임시 이미지) | **텍스트 문항 탐지 신뢰도 65% 미만일 때만** 페이지마다 | 페이지 전체를 그린 JPEG(1.15배, 화질 .72), 파일명 `<PDF 파일명>_page<N>.jpg`, `kind=problem-page-segmentation`. 처리 후 `DELETE /photo` 시도 | 8308–8311, 8109, 8129 |
| `POST /segment-problem-page` | 위와 같은 조건 | JSON: 방금 올린 임시 이미지의 저장 키, 쪽 번호, **PDF 파일명** | 8114 |

| `GET /photo?key=` | 사진 표시 | 토큰 없이 주소만(이미지 태그/`fetch` 에 인증 헤더 없음) | 1191–1195, 1113–1157 |

**모든 `POST/DELETE` 헤더:** `Authorization: Bearer <로그인 중인 Firebase 사용자의 ID 토큰>`(1218–1222)과 `X-MNM-Role: director|student`(앱이 스스로 적는 값). 원장도 현재 비밀번호 방식(익명 로그인)이므로 토큰은 익명 세션 토큰이다.

**보내지 않는 것(코드 근거):** PDF 원본 파일 — PDF 는 브라우저 안에서만 읽고(`file.arrayBuffer()` → pdf.js, 8303) 어떤 `fetch` 에도 실리지 않는다. PDF 수집 요청에는 학생 이름·학생 id·반 정보가 없다. 앱의 다른 `fetch` 는 이미지 표시용 GET 뿐이다(위 목록이 전부).

**주의할 점:** ① PDF **파일명**이 업로드 파일명과 분리 요청 본문에 그대로 실린다(교재명 등이 있으면 노출). ② 문항 이미지는 PDF 안 내용 그대로다(교재 저작물일 수 있음). ③ 학생 질문 사진이 올라오면 PDF 시험과 무관하게 **지금도 자동으로** `/analyze-problem` 이 호출된다(이미지 저장 키와 질문 글 포함).

**코드로 확인할 수 없는 것 (미확인):** 서버가 이 경로들을 실제로 제공하는지 · 토큰을 검증하는지(`X-MNM-Role` 은 자기 신고 값) · `category`/`studentId` 값을 받아들이는지 · 이미지를 어디에 얼마나 보관하는지 · `/segment-problem-page`·`/analyze-problem` 이 이미지를 외부 AI 업체로 보내는지 · `/photo` 조회에 인증이 필요한지(이미지 태그는 헤더를 못 보내므로 저장 키를 아는 사람이 볼 수 있을 가능성) · 삭제가 서버에서 실제로 되는지.

## 4. 합성 PDF 수집 시험 1회 결과 (2026-10-20, 개발 환경 — **실제 운영 환경 검증 아님**)
**조건:** `tests/fixtures/sample-problems.pdf`(영문 합성 3문항, 개인정보·교재 없음)만 사용. 앱은 저장소의 `index.html` 을 로컬에서 실행, Firestore 는 메모리 가짜(운영 Firebase 접속 없음), 로그인 토큰은 가짜 문자열(실제 자격 증명 아님), pdf.js 는 로컬 파일. 서버 주소만 실제(`mnm-photo-api.jihagondu.workers.dev`). 추가 호출·재시도 없음.

**실제로 전송을 시도한 요청(1건, 코드 확인 내용과 일치):** `POST …/upload`, 헤더 `Authorization: Bearer <가짜 토큰>`·`X-MNM-Role: director`, 본문 multipart = `file`(`sample-problems_q01.jpg`, image/jpeg, 11,007바이트) + `kind=problem-crop` + `category=problem-crop` + `studentId=problem-bank`. 학생 정보·PDF 원본·PDF 글자 내용 없음. 첫 요청이 실패하자 앱이 즉시 중단해 나머지 문항 이미지(2장)는 전송을 시도하지 않음.

**결과: 실패 — 서버에 도달하지 못함.** 브라우저 오류 `net::ERR_TUNNEL_CONNECTION_FAILED`(이 개발 환경의 프록시 터널 단계에서 연결 실패). **원인은 확정되지 않았다 — 서버 장애로도, 서버 정상으로도 결론 내리지 않는다.** Worker 의 실제 동작은 **미확인**이며 같은 요청을 반복하지 않았다. 서버 응답 없음(상태 코드 없음).
- 앱 화면: 상태 줄 `자동분리 중단 · Failed to fetch`, 알림창 `PDF 자동분리를 완료하지 못했습니다.\nFailed to fetch`.
- 생성·저장된 데이터: 서버 이미지 **0장**(요청이 서버에 도달하지 못함 — 서버 쪽 수신 여부는 이 환경에서 확인할 수 없어 엄밀히는 미확인이나 터널 단계에서 거절됨), 메모리 가짜의 초안·출처 **0건**, 운영 Firestore 변경 **없음**. 삭제할 것 없음.
- 서버 경로 존재, 토큰 검증, 문항 이미지 수용, 저장·삭제 동작: **전부 미확인**(응답이 없었으므로 이번 시험으로는 알 수 없음).

**운영 화면에서 같은 문구가 나올 때 해석:** 서버 거절이면 `R2 upload 401` 처럼 숫자가 붙은 문구나 서버의 `error` 문구가 나온다. `Failed to fetch` 는 서버 응답 자체를 받지 못한 경우(네트워크 차단·서버 주소 오류·서버 CORS 설정 등)다. 실제 운영 검증은 원장님 기기에서 해야 하며 **미완료**다.

## 6. 별도 테스트 환경에서 실제 업로드를 확인하는 방법 (제안 · 아직 만들지 않음)
**왜 필요한가:** 코드와 가짜 서버로는 "실제 Worker 가 `problem-crop` 이미지를 받는지, 토큰을 검증하는지, 저장·삭제가 되는지"를 알 수 없다. 이것만 남는다.
**방법(운영 데이터와 완전히 분리):**
1. Firebase 에서 **시험용 새 프로젝트**를 만든다(익명 로그인 + Firestore, 시험용 규칙). 운영 프로젝트는 건드리지 않는다.
2. Cloudflare 에서 **시험용 이름으로 Worker 와 R2 버킷을 새로 만든다.** 운영 Worker 의 코드를 대시보드에서 복사해 시험용으로 배포하면 "실제 코드"의 동작을 운영 데이터 없이 볼 수 있다(코드는 원장님 계정에서만 볼 수 있음. 비밀값은 복사하지 않고 시험용으로 새로 설정).
3. `index.html` 사본에서 `PHOTO_API_BASE` 와 Firebase 설정(`firebaseConfig`)만 시험용 값으로 바꿔 **로컬 또는 시험 프로젝트 호스팅**에서 연다. (운영 앱에 "주소 바꾸기" 옵션을 넣지 않는다 — 토큰이 엉뚱한 곳으로 가는 통로가 되기 때문.)
4. 합성 PDF 로 수집 → **생성되는 데이터:** 시험 Firestore 에 초안·출처, 시험 R2 에 문항 이미지(스캔형이면 임시 페이지 이미지도).
5. **확인:** Firestore 콘솔에서 `problemDrafts` 의 `storageKey` 와 `data:image` 가 아닌지 · R2 콘솔 객체 목록 · 앱에서 이미지 표시 · 삭제 요청 후 객체가 실제로 사라졌는지.
6. **정리:** 시험 프로젝트와 시험 R2 버킷을 통째로 삭제하면 끝. 운영에는 아무것도 남지 않는다.
**운영 앱에서만 할 수 있는 단계:** 운영 Worker 가 운영 환경(실제 도메인·CORS·토큰 검증 설정)에서 동작하는지는 시험 환경에서 같지 않을 수 있다. 이 단계는 위 시험이 모두 끝나고, 합성 PDF 로 **원장님이 직접** 하는 최종 1회다. 영향: 운영 R2 에 문항 이미지 3장, 운영 Firestore 에 수집 초안 3건·출처 1건(앱에 초안 삭제 버튼이 없어 Firebase 콘솔에서 직접 삭제해야 함), 삭제 시 서버 이미지가 실제로 지워지는지는 별도 확인 필요. 원장님이 원하지 않으면 하지 않아도 된다(미확인으로 남음).
