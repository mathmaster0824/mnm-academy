# 보안 1단계 — 운영 전환 판단 자료 (원장용)

> **상태: 아무것도 운영에 적용하지 않았다.** PR #13 은 draft 이며 병합·배포·운영 계정 생성·실제 규칙 배포·데이터 변경을 하지 않았다.
> 이 문서는 "전환할지, 어떤 순서로 할지"를 판단하기 위한 자료다. 절차 자체는 `SECURITY_PHASE1_CUTOVER.md` 참고(이 문서의 §2 순서가 우선하며, 그 문서도 이에 맞춰 고쳤다).

## 먼저 결론

1. **앱만 먼저 배포하면 보안은 하나도 좋아지지 않는다.** 지금 Firestore 규칙은 "로그인한 세션이면 전부 읽기·쓰기"라서, 앱을 `firebase` 모드로 바꿔도 **원장 비밀번호(`meta/settings`)와 원장 권한 목록(`meta/directors`)은 기존 넓은 규칙으로 계속 읽히고 심지어 수정도 된다.** 앱이 더 이상 읽지 않을 뿐, 서버가 막아 주지 않는다. 공개된 웹 키로 누구나 익명 로그인을 만들 수 있으므로 앱을 거치지 않고도 읽힌다(이미 지금 그렇다).
2. **규칙을 먼저 배포하면 모두가 멈춘다.** 현재 앱은 로그인 전에 `meta/settings` 를 읽는데 새 규칙은 이를 막는다 → 모든 접속자 무한 로딩. 그래서 순서는 반드시 **앱 → 규칙**이고, 둘 사이를 짧게 하는 것이 핵심이다.
3. **새로 생기는 위험이 하나 있다(§3-A).** 이메일/비밀번호 로그인을 켜면 누구나 웹 키로 계정을 만들 수 있다. 규칙 배포 전에는 `meta/directors` 가 아무에게나 수정 가능하므로, 그 사이에 공격자가 자기 계정을 허용 목록에 넣을 수 있다. → 계정 생성~규칙 배포를 한 번에 끝내고, 배포 직전·직후에 목록을 확인하는 순서로 바꿨다.

## 1. `DIRECTOR_AUTH` 를 firebase 모드로 바꾸는 정확한 위치

- 파일 `index.html`, **276번째 줄** (PR #13 기준). 지금 값:
  `const DIRECTOR_AUTH = { mode:'legacy', email:'director@REPLACE-ME.invalid' };`
- 바꿀 값: `{ mode:'firebase', email:'<Firebase 에 만든 원장 계정 이메일>' }` — **이 두 값만** 바꾼다. 비밀번호는 코드에 넣지 않는다(로그인 화면에서 원장님이 입력).
- 주의
  - 이메일은 공개 저장소·웹 페이지에 그대로 보인다(비밀 값이 아님). 대신 **비밀번호가 약하면 누구나 대입 시도를 할 수 있다** → 12자 이상, 다른 곳에서 쓰지 않은 값. Firebase 가 시도 횟수를 제한하지만 방패는 비밀번호 강도다.
  - `REPLACE-ME` 가 남아 있으면 앱이 "원장 로그인 설정이 아직 끝나지 않았어요"라고 막는다(실수 방지).
  - 시험에서는 이 값이 메모리에서만 바뀌었고, 저장소 파일은 `legacy` 그대로다.

## 2. 권장 순서와 각 단계의 효과 (보안 공백을 줄인 순서)

"효과"는 그 단계 직후 **보안이 실제로 달라지는가**를 뜻한다.

| 순서 | 할 일 | 하는 사람 | 보안 효과 | 끊길 수 있는 곳 |
|---|---|---|---|---|
| 0 | **사전 준비(영향 없음)**: PR #13 시험 결과 재확인, 학생 접속이 적은 시간 선택, 학생 앱 새로고침 안내문 준비, 현재 규칙 텍스트 복사·저장, 앱 내 백업 실행 | 원장 | 없음 | 없음 |
| 1 | **계정 생성 + 허용 목록을 한 번에(가능하면 30분 안에 끝까지)**: ① Authentication 에서 이메일/비밀번호 켜기 ② 원장 계정 만들기(강한 비밀번호) ③ UID 복사 ④ Firestore `meta/directors` 문서(`uids` 배열)에 그 UID 만 넣기 ⑤ 콘솔에 "계정 생성(sign-up) 허용" 설정이 보이면 **끄기**(보이는지는 실제 화면 확인 필요 — 본 환경에서 확인 못 함) | 원장 | **없음, 오히려 §3-A 위험 시작** | 없음 |
| 2 | **앱 배포**: `index.html` 276번째 줄 변경 후 배포(별도 승인) | 원장 승인 → 개발 담당 | **없음.** 비밀번호·허용 목록은 여전히 읽힘/쓰기 가능 | 아래 §4-② |
| 3 | **앱 검증(5분 이내)**: 원장 새 비밀번호 로그인, 학생 코드 로그인·숙제 제출. 콘솔에서 Users 목록에 원장 계정**만** 있는지, `meta/directors.uids` 가 원장 UID**만**인지 확인 | 원장 | 없음 | — |
| 4 | **규칙 배포(콘솔에서 직접)**: 1단계 규칙 게시 → 곧바로 §5 최소 기능 점검 | 원장 | **여기서 처음 보안이 개선된다** (§3 참고) | 아래 §4-③ |
| 5 | **관찰(며칠)**: 빈 화면·권한 오류 확인 | 원장 | — | — |
| 6 | **옛 비밀번호 삭제(별도 승인)** 및 옛 비밀번호 폐기(어디서도 재사용 금지) | 원장 승인 | 노출된 옛 값이 DB 에서도 사라짐 | — |

공백 줄이는 원칙
- 지금도 이미 열려 있다. **단계 2~4 사이는 "지금보다 나빠지지는 않지만 좋아지지도 않는" 구간**이고, 새 위험은 단계 1~4 사이의 허용 목록 변조뿐이다. 그래서 1→4 를 같은 날 한 번에 끝낸다. 중간에 멈추면 §6 처럼 되돌린다.
- 단계 3 에서 허용 목록과 사용자 목록을 **눈으로 확인**하고, 단계 4 직후 **한 번 더** 확인한다(이상한 계정·UID 가 있으면 즉시 삭제 후 진행).
- 앱 배포(2)와 규칙 배포(4)의 간격은 **검증에 필요한 시간(수 분)**만 둔다. GitHub Pages 반영·브라우저 캐시 때문에 앱이 실제로 바뀌었는지 새 브라우저에서 확인한 뒤에만 4 로 간다.

## 3. 현재 규칙이 유지되는 동안 남는 위험 (단계 4 전까지)

지금 규칙은 `allow read, write: if request.auth != null` 한 줄이다. 공개된 웹 키로 누구나 익명 로그인을 만들 수 있으므로 **앱 없이도** 다음이 가능하다.

- 모든 학생의 이름·코드(4자리)·학습·성적·사진·메모·월말 관련 데이터 **열람**
- 원장 비밀번호(평문) 열람 → 원장 화면 접속
- 모든 데이터 **수정·삭제**(학생 코드, 출결, 성적, 숙제 승인, 문제 정답 등)
- 문제저장소 정답키 열람·변조

### 3-A. 전환 중에 새로 생기는 위험
- 이메일/비밀번호 로그인을 켜면 같은 웹 키로 **계정 생성**이 가능해진다(콘솔에서 막는 설정이 있다면 사용). 규칙 배포 전에는 `meta/directors` 를 아무나 고칠 수 있으므로, 공격자가 ① 계정을 만들고 ② 자기 UID 를 `uids` 에 넣어 두면 **규칙 배포 후 그 계정이 원장 권한**을 갖는다.
- 완화: 위 §2 의 "한 번에 끝내기 + 배포 직전·직후 Users 목록/`uids` 확인". 새 규칙이 올라간 뒤에는 `meta/directors` 는 원장만 수정할 수 있어 이 경로가 닫힌다.
- 이 위험은 규칙을 배포하지 않고 이메일/비밀번호만 켜 두는 기간이 **길수록** 커진다.

### 3-B. 규칙 배포 후에도 남는 노출
- 옛 `adminPassword` 값이 DB 에 남아 있다(단계 6 전). 이미 노출된 적이 있으므로 **그 값은 폐기된 것으로 취급**한다.
- 원장 이메일이 공개 코드에 보인다 → 비밀번호 강도에 의존.

## 4. 전환 중 끊길 수 있는 지점과 증상

① **단계 1(준비)**: 영향 없음.
② **단계 2(앱 배포) 직후**
- 원장: **옛 비밀번호(0000 등)는 앱에서 거부**된다. 새 비밀번호만 통한다. 이메일 오타·계정 미생성이면 원장 로그인이 안 된다 → 앱을 `legacy` 로 되돌리면 즉시 복구(규칙은 아직 옛 규칙).
- 이전에 원장 PC 에 저장된 로그인 상태는 복원되지 않는다(서버 로그인만 인정) → 한 번 다시 로그인.
- 학생: 변화 없음. 이미 열려 있는 옛 화면은 옛 방식으로 계속 동작.
③ **단계 4(규칙 배포) 직후** — 가장 위험한 순간
- **옛 앱을 그대로 열어 둔 기기**(캐시, 홈 화면 바로가기, 탭을 오래 열어 둔 폰): 옛 앱은 시작 때 `meta/settings` 를 읽는데 거부되어 **무한 로딩**. 새로고침(완전히 닫았다 열기)하면 해결.
- 학생이 로그인한 채 쓰고 있던 옛 화면: 연결 상태 표시가 끊김으로 나오거나 일부 저장이 실패할 수 있음.
- 시험에서 다루지 못한 경로: 코드 읽기로 만든 컬렉션 목록 밖에 학생 세션이 쓰는 곳이 있으면 거부된다(원장 전용 기본값). 증상은 "특정 화면에서 저장이 안 됨".
- 사진 업로드: 외부 Worker 가 Firebase 토큰을 어떻게 검증하는지 **확인하지 못함** → 반드시 실기기 확인(§7).
④ **원장 비밀번호 분실**: 비밀번호 재설정 메일은 실제 받을 수 있는 이메일일 때만 동작. 콘솔(Authentication)에서 비밀번호를 직접 재설정할 수 있다.
⑤ **로그인 시도 과다**: Firebase 가 잠시 차단("시도가 너무 많아요") — 몇 분 뒤 재시도.

## 5. 단계별 확인 방법과 되돌리는 방법

| 시점 | 확인 | 이상 시 되돌리기 |
|---|---|---|
| 단계 1 후 | Users 에 원장 계정 1개, `meta/directors.uids` = [원장 UID] | 계정/문서 삭제(영향 없음) |
| 단계 2·3 | 새 브라우저(시크릿 창)에서 원장 새 비밀번호 로그인, 옛 비밀번호 거부, 학생 코드 로그인·숙제 제출 | 앱을 `legacy` 판으로 재배포 (규칙은 아직 옛 규칙이라 안전하게 복구됨) |
| 단계 4 직후 | §7 최소 기능 점검 전부, Users·`uids` 재확인 | **규칙부터 되돌린다**: Firestore 규칙 탭의 기록에서 이전 버전 게시(또는 저장해 둔 텍스트 재게시). 데이터는 변하지 않음 |
| 단계 5 | 며칠간 빈 화면·권한 오류 제보 수집 | 규칙 문제면 규칙 보강(개발 담당) 또는 일시 되돌리기 |

되돌림 순서 원칙: **적용은 앱 → 규칙, 되돌림은 규칙 → 앱.** 규칙이 새 상태에서 앱만 `legacy` 로 돌리면 로딩이 막힌다.

## 6. 1단계로 해결되지 않는 것 (규칙 배포 후에도 남음)

- **학생 간 자료 열람**: 학생 세션이 "누구인지" 서버가 모른다(모두 익명). 학생 A 의 세션이 학생 B 의 질문·제출·성적·사진 등을 읽을 수 있고, `students` 문서의 4자리 코드도 전 학생이 읽을 수 있다 → 타 학생 코드로 로그인(사칭) 가능. *(E2E 에서 "알려진 한계"로 고정해 확인함)* 해결: 2단계(서버가 코드 확인 후 학생별 토큰 발급).
- **문제저장소 직접 쓰기**: 학생 세션이 `problems`·`problemKeys`·`problemDrafts`·`problemSources` 를 읽고 쓸 수 있다(질문 올리기 때 학생 세션이 쓰기 때문). **정답키도 읽힌다.** 해결: 문제저장소 작업에서 서버 처리로 이전한 뒤 닫기. *(E2E 에서 확인)*
- **여러 학생 기록이 한 문서에 있는 구조**: `classRecords`·`weeklyPlans`·`fridaySupp` 는 반 단위 한 문서에 같은 반 학생 전원의 출결·점수·계획이 들어 있어, 읽기를 열면 전원이 보이고 학생별로 막을 수 없다. 해결: 학생별 사본으로 분리(2단계 설계).
- 그 밖: 숙제 `reviewCount` 등 앱이 정해 보내는 값을 학생이 위조하는 것, 월말 리포트 **앱 기능** 잠금은 PR #11 상태 그대로(규칙상 원장 전용이 될 뿐 기능이 풀린 것은 아님), 옛 `adminPassword` 삭제는 별도 승인.

## 7. 운영 전환 전 실제 기기에서 확인할 최소 기능 목록

시험은 에뮬레이터·가짜 데이터였다. 아래는 **실제 기기·실제 프로젝트**에서만 확인할 수 있다. (앱 배포 후, 규칙 배포 **전** 한 번 / 규칙 배포 **직후** 한 번, 총 두 번)

원장 (PC + 폰 각 1회)
1. 새 비밀번호로 로그인 되고, 옛 비밀번호는 거부된다
2. 로그인 후 학생·반 목록, 오늘의 반 화면이 뜬다
3. 숙제 승인/보완 처리와 코멘트 저장이 된다
4. 새로고침 후에도 로그인이 유지된다 / 로그아웃 후 학생 모드 입장이 된다
5. 비밀번호 변경 패널이 동작한다(시험용으로 바꿨다면 반드시 다시 안전한 값으로)
6. 전체 백업이 완료된다(백업 파일은 원장님 기기에만)
7. 월말 리포트 화면이 PR #11 상태 그대로(생성 불가)다 — **초안 생성 버튼은 누르지 않는다**

학생 (실제 학생 폰 2종 이상, 학생 코드는 본인 것 또는 테스트용으로)
8. 학생 코드로 입장되고 오늘 숙제 화면이 뜬다
9. **사진 첨부 숙제 제출**(외부 Worker 업로드 포함)이 되고, 원장 화면에서 사진이 보인다
10. 질문 올리기(사진 포함)가 되고 원장이 답변하면 학생이 본다
11. 공부 타이머 시작·정지, 주말 학습 인증, STAD 신청/기록이 저장된다
12. 앱을 닫았다 열어도 로그인 유지 / 옛 홈 화면 바로가기에서 열었을 때 무한 로딩이 없는지

공통
13. 규칙 배포 후 **시크릿 창에서 학생 코드 입력 없이** 첫 화면까지 로딩이 끝난다
14. 콘솔 Users 에 원장 계정만 있고 `meta/directors.uids` 가 원장 UID 뿐이다

하나라도 실패하면 §5 대로 규칙부터 되돌리고 개발 담당에게 증상(화면·시각)만 알려 달라. 학생 이름·내용·비밀번호는 보내지 않는다.

## 8. 아직 확인하지 못한 것 (판단 시 감안)
- 콘솔에 "계정 생성 허용 끄기" 옵션이 이 프로젝트에 있는지
- 사진 업로드 Worker 의 토큰 검증 방식
- 홈 화면 바로가기/캐시된 옛 앱 비율
- 코드 읽기로 만든 컬렉션 목록 밖의 학생 쓰기 경로 유무
- 부하·지연·실제 기기 차이
