# 보안 1단계 — 운영 전환 판단 자료 (원장용)

> **상태: 아무것도 운영에 적용하지 않았다.** PR #13 은 draft 이며 병합·배포·운영 계정 생성·실제 규칙 게시·데이터 변경을 하지 않았다.
> 한 단계씩 따라 하는 절차는 `SECURITY_PHASE1_CUTOVER.md`. 이 문서는 "왜 이 순서인지, 무엇이 남는지"를 설명한다.
> (개정: 허용 목록 문서 방식을 **규칙에 원장 UID 직접 기재** 방식으로 교체했다. 이전 판의 "배포 전후 목록 확인" 완화책과 "계정 생성 허용 끄기" 권고는 철회했다.)

## 먼저 결론

1. **앱만 먼저 배포하면 보안은 좋아지지 않는다.** 지금 규칙은 "로그인한 세션이면 전부 읽기·쓰기"라서 앱을 `firebase` 모드로 바꿔도 원장 비밀번호(`meta/settings`)는 계속 읽힌다(수정도 된다). 공개 웹 키로 누구나 익명 로그인을 만들 수 있어 앱 없이도 읽힌다 — 이미 지금 그렇다. 보안이 실제로 좋아지는 것은 **규칙을 게시하는 순간**부터다.
2. **규칙을 먼저 게시하면 모두가 멈춘다.** 현재 앱이 로그인 전에 `meta/settings` 를 읽는데 새 규칙이 막기 때문이다. 순서는 **앱 → 규칙**, 되돌릴 때는 **규칙 → 앱**.
3. **원장 권한을 Firestore 문서(`meta/directors`) 목록으로 판정하면 권한 탈취 경로가 생긴다.** 옛 규칙에서는 아무 세션이나 그 문서를 쓸 수 있고, 이메일/비밀번호 로그인을 켜면 누구나 계정을 만들 수 있다. 규칙 배포 전에 자기 UID 를 목록에 넣어 두면 배포 뒤 원장이 된다. 배포 전후에 목록을 눈으로 확인하는 것은 **탐지일 뿐 예방이 아니다**(확인과 게시 사이에 다시 쓸 수 있고, 게시 후 발견하면 그 사이 이미 권한이 열려 있었다).
4. **그래서 이 PR 은 원장 UID 를 규칙 파일에 직접 적는 방식을 쓴다.** 규칙은 콘솔에서만 고칠 수 있어 공개 클라이언트가 바꿀 수 없다. 계정 생성이 열려 있는 기간이 길어도 다른 계정은 원장이 되지 못한다(익명 세션과 같은 권한뿐).

## 1. `DIRECTOR_AUTH` 를 firebase 모드로 바꾸는 위치
- `index.html` **276번째 줄 부근**: `const DIRECTOR_AUTH = { mode:'legacy', email:'director@REPLACE-ME.invalid' };`
- 바꿀 값: `{ mode:'firebase', email:'<Firebase 에 만든 원장 계정 이메일>' }`. 비밀번호·UID 는 이 코드에 넣지 않는다.
- 이메일은 공개 코드에 보인다(비밀 아님). 대신 비밀번호가 약하면 대입 시도를 받을 수 있으니 **12자 이상**. `REPLACE-ME` 가 남아 있으면 앱이 막는다.
- **원장 UID 는 앱이 아니라 Firestore 규칙 파일에만** 적는다: `security/firestore.rules.phase1.proposed` 의 `directorUids()` — 저장소에는 자리표시자 `REPLACE_WITH_DIRECTOR_UID` 만 있고, 게시 때 원장님이 콘솔에서 확인한 UID 로 바꿔 게시한다. UID 는 비밀값이 아니다(비밀번호·API 비밀키와 다름). 자리표시자 그대로 게시하면 아무도 원장이 되지 못한다(학생 기능은 유지).

## 2. 순서와 각 단계의 효과
(자세한 확인 방법·실패 시 증상은 CUTOVER 문서의 표)

| 순서 | 할 일 | 보안 효과 |
|---|---|---|
| 1 | 사전 준비(규칙 텍스트 저장, 백업, 시간 선택) | 없음 |
| 2 | 이메일/비밀번호 켜기 + 원장 계정 생성(본인 생성 확인) | **없음.** 계정 생성이 열린 기간이 시작되지만 UID 규칙 방식이라 권한 탈취 경로 없음 |
| 3 | 앱 배포(`firebase` 모드) | **없음**(옛 규칙: 비밀번호 문서는 여전히 읽힘) |
| 4 | 로그인한 본인 계정의 UID 를 규칙 텍스트에 기재(게시 전) | 없음 |
| 5 | 규칙 게시(콘솔, 4 직후) | **여기서 처음 개선**: 비밀번호 문서·월말 리포트·학생/반 데이터 수정 차단, 원장 전용 상태값 보호 |
| 6~8 | 확인, 관찰, (별도 승인) 옛 비밀번호 삭제 | 옛 값 제거 |

- **보안 공백**은 규칙을 게시하기 전까지 현재 규칙이 유지되는 기간 전체이고, 노출 범위는 지금과 같다(§3). 이 기간에 **새로 늘어나는 노출은 없다.** 공백을 줄이려면 2~5단계를 같은 날 이어서 한다.
- 게시한 뒤 원장을 바꾸거나 추가하려면 규칙의 UID 를 고쳐 **다시 게시**해야 한다.

## 3. 현재 규칙이 유지되는 동안 남는 위험 (5단계 전까지)
공개된 웹 키로 누구나 익명 로그인을 만들 수 있으므로 앱 없이도 다음이 가능하다: 모든 학생의 이름·코드·학습·성적·사진·메모 열람, 원장 비밀번호(평문) 열람, 모든 데이터 수정·삭제, 문제저장소 정답키 열람·변조.
규칙 게시 뒤에도 남는 것: 옛 `adminPassword` 값이 DB 에 남아 있음(8단계 전, 노출된 적이 있으므로 폐기 취급), 원장 이메일이 공개 코드에 보임(비밀번호 강도에 의존).

## 4. 전환 중 끊길 수 있는 지점
- **3단계(앱 배포) 직후**: 원장 옛 비밀번호 거부(새 비밀번호만 통함), 원장 PC 에 저장돼 있던 로그인 상태는 복원되지 않음(다시 로그인). 이메일 오타·계정 미생성이면 원장 로그인 불가 → 앱을 `legacy` 로 재배포하면 즉시 복구(규칙은 옛 규칙).
- **5단계(규칙 게시) 직후 — 가장 위험**: 옛 앱을 열어 둔 기기(캐시·홈 화면 바로가기·오래 열어 둔 탭)는 무한 로딩(새로고침으로 해결). **UID 오기재** 시 원장만 거부됨(규칙의 UID 수정 후 재게시, 학생은 영향 없음). 코드 읽기로 만든 컬렉션 목록 밖의 학생 쓰기 경로가 있으면 그 화면에서 저장 실패. 사진 업로드 서버가 로그인 토큰을 어떻게 검증하는지는 확인하지 못했다.
- **원장 비밀번호 분실**: 콘솔(Authentication)에서 재설정 가능.
- **로그인 시도 과다**: Firebase 가 잠시 차단 → 몇 분 뒤 재시도.

## 5. 되돌리기
규칙 문제 → **이전 규칙 게시**(저장한 텍스트·규칙 기록) → 필요하면 그다음 앱을 `legacy` 로. 규칙이 새 상태일 때 앱만 `legacy` 로 돌리면 로딩이 막히므로 항상 **규칙 먼저**.

## 6. 1단계로 해결되지 않는 것
- **학생 간 자료 열람**: 학생 세션이 "누구인지" 서버가 모른다(모두 익명). 학생 A 세션이 학생 B 의 질문·제출·성적·사진을 읽을 수 있고 `students` 의 4자리 코드도 전 학생이 읽을 수 있다 → 타 학생 사칭 가능. (E2E "알려진 한계"로 고정) 해결은 2단계.
- **문제저장소 직접 쓰기**: 학생 세션이 `problems`·`problemKeys`·`problemDrafts`·`problemSources` 를 읽고 쓸 수 있다(정답키 포함). 문제저장소 작업에서 서버 처리로 옮긴 뒤 닫는다.
- **여러 학생 기록이 한 문서에 있는 구조**: `classRecords`·`weeklyPlans`·`fridaySupp` 는 반 단위 한 문서에 전원의 출결·점수·계획이 있어 학생별로 막을 수 없다. 2단계에서 학생별 사본으로 분리.
- 그 밖: 숙제 `reviewCount` 등 앱이 정해 보내는 값 위조, 월말 리포트 **앱 기능** 잠금은 PR #11 상태 그대로(규칙상 원장 전용이 될 뿐 기능이 풀린 것은 아님), 옛 `adminPassword` 삭제는 별도 승인.

## 7. 실기기 확인 최소 목록
CUTOVER 문서의 "실기기 확인 목록"(원장 6개·학생 5개·공통 1개)을 앱 배포 후 규칙 게시 전, 규칙 게시 직후 두 번 확인한다.
