# 보안 1단계 — 운영 전환 절차 (원장용)

> 상태: **준비만 됨. 운영에는 아무것도 적용하지 않았다.** 이 문서의 순서대로, 원장님이 직접 승인하고 하나씩 진행한다.
> 비밀번호·계정 정보는 개발 담당(Claude)에게 보내지 않는다. 모든 비밀번호 입력은 원장님이 직접 한다.

## 1단계가 해결하는 것 / 해결하지 않는 것

| 해결(전환을 끝까지 마쳤을 때) | 해결하지 않음 (2단계 이후 별도 작업) |
|---|---|
| 원장 비밀번호를 학생 세션이 읽지 못함(서버 로그인으로 대체) | 학생이 **다른 학생의 자료**를 읽는 것 (학생 세션이 누구인지 서버가 모름, `students.code` 도 전 학생이 읽을 수 있음) |
| 학생 세션이 학생·반·성적·출결 등 원장 관리 데이터를 수정하는 것 | 학생이 **문제저장소(problems·problemKeys·problemDrafts·problemSources)에 직접 쓰기** — 정답키도 계속 읽힘. 문제저장소 작업에서 서버 처리로 옮긴 뒤 닫는다 |
| 월말 리포트·피드백·해설 사진·집중 기록 접근(원장 전용) | **한 문서에 여러 학생 정보**가 들어 있는 구조(classRecords·weeklyPlans·fridaySupp). 2단계에서 학생별 사본으로 분리 |
| 숙제 승인·STAD 승인/출석·질문 답변·주말학습 수동인정을 학생 세션이 조작하는 것 | 숙제의 `reviewCount` 등 앱이 정해 보내는 값을 학생이 바꾸는 것 |

- **월말 리포트**: 규칙으로 원장 전용이 되지만, 앱의 월말 리포트 기능은 PR #11 의 잠금(`MONTHLY_REPORT_CLIENT_ENABLED=false`)이 그대로이며 이번에 풀지 않았다. 잠금이 풀렸다는 뜻이 아니다.
- **원장 비밀번호 문제**: 전환을 끝까지 마치고 `meta/settings` 의 `adminPassword` 값을 지우기(별도 승인) 전까지는 "해결"이 아니다. 규칙 배포 전에는 옛 비밀번호가 여전히 읽힌다.

## 전환 순서 (한 단계씩)

각 단계 끝의 **확인**을 통과해야 다음으로 간다. 막히면 멈추고 알려 달라.

1. **PR #13 확인.** GitHub PR 댓글의 시험 결과(규칙 시험·E2E)가 모두 통과인지 확인한다. 실패가 있으면 여기서 멈춘다. (이 PR 은 draft 이며 병합하지 않은 상태)
2. **Firebase 콘솔 → Authentication → Sign-in method** 에서 **이메일/비밀번호** 제공업체를 사용 설정한다. 익명(Anonymous)은 그대로 켜 둔다(학생이 계속 쓴다).
   - 확인: 두 제공업체(익명, 이메일/비밀번호)가 "사용 설정됨".
3. **Authentication → Users → 사용자 추가**: 원장용 이메일과 **새 비밀번호(6자 이상)** 를 원장님이 직접 입력해 계정을 만든다. 쓰는 이메일은 실제 받는 주소가 아니어도 된다(예: 본인 소유 주소 권장). 지금 쓰는 비밀번호 `0000` 은 6자 미만이라 쓸 수 없다.
   - 확인: 목록에 계정이 보이고 **사용자 UID** 칸이 있다. 이 UID 를 복사해 둔다(비밀 값 아님).
4. **Firestore → 데이터 → `meta` 컬렉션에 문서 추가**: 문서 ID `directors`, 필드 `uids` (유형 **array**), 값에 3단계의 UID 문자열 1개. *(규칙을 아직 배포하지 않았으므로 지금은 아무 영향이 없다. `meta` 의 다른 문서는 건드리지 않는다.)*
   - 확인: `meta/directors` 문서에 `uids` 배열이 있다.
5. **앱 코드 반영**(개발 담당에게 요청): `index.html` 의 `DIRECTOR_AUTH` 를 `{ mode:'firebase', email:'<3단계 이메일>' }` 로 바꾼 버전을 **별도 승인 후** 배포한다. 이 시점에도 규칙은 아직 옛 규칙이라 모두 정상 동작해야 한다.
   - 확인(원장 PC): 원장 모드에서 **3단계에서 정한 새 비밀번호**로 입장된다. 옛 비밀번호 `0000` 은 거부된다.
   - 확인(학생): 학생 모드 4자리 코드로 입장·숙제 제출이 평소처럼 된다.
   - **이미 열어 둔 옛 앱(캐시)** 은 5단계 이후에도 옛 방식으로 동작하려 하므로, 6단계 전에 학생들에게 앱을 새로고침(완전히 닫았다 열기)하게 안내한다.
6. **규칙 배포 (원장님이 Firebase 콘솔에서 직접)**: Firestore → 규칙 탭에서 현재 규칙을 **복사해 따로 저장**(되돌리기용)한 뒤, `security/firestore.rules.phase1.proposed` 내용을 붙여넣고 게시한다. 학생 접속이 적은 시간대를 권장한다.
   - 확인(바로): 원장 로그인·원장 화면 목록 로딩, 학생 코드 입장·숙제 제출·질문 올리기, 학생 폰에서 로딩이 끝까지 되는지(무한 로딩 아님).
   - 문제가 생기면 **즉시 되돌리기**: 규칙 탭의 "기록(History)"에서 이전 버전을 게시하거나 저장해 둔 규칙을 다시 게시. (데이터는 변하지 않는다.)
7. **하루~며칠 관찰.** 학생·원장 화면에서 "권한 없음"으로 빈 화면이 되는 곳이 없는지 확인한다. 있으면 어디인지 알려 달라(규칙 보강).
8. **(별도 승인) 옛 비밀번호 삭제.** 7단계가 안정된 뒤에만 `meta/settings` 의 `adminPassword` 필드를 지운다. 이 단계 전에는 옛 비밀번호가 이미 노출된 적이 있으므로 새 비밀번호와 **다른 값**을 쓴다.

## 되돌리기(롤백)

- 규칙만 문제: 6단계 규칙을 이전 버전으로 되돌린다 → 모든 로그인 세션이 다시 읽기/쓰기 가능(옛 상태).
- 앱 로그인 문제: `DIRECTOR_AUTH.mode` 를 `'legacy'` 로 되돌린 버전을 배포한다(단, 규칙이 1단계 상태면 `legacy` 는 `meta/settings` 를 못 읽어 로딩이 막히므로 **규칙을 먼저 되돌린다**).
- 순서 원칙: 적용은 앱 → 규칙, 되돌릴 때는 규칙 → 앱.
