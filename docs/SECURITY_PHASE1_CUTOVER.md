# 보안 1단계 — 운영 전환 절차 (원장용)

> 상태: **준비만 됨. 운영에는 아무것도 적용하지 않았다.** 아래는 원장님이 직접 승인하고 하나씩 진행하는 절차다.
> 비밀번호·API 비밀키는 개발 담당(Claude)에게 보내지 않는다. 비밀번호 입력은 원장님이 직접 한다. (원장 UID 는 비밀값이 아니라서 규칙 파일에 적어도 된다.)
> 판단 근거와 위험은 `SECURITY_PHASE1_DECISION_BRIEF.md` 참고.

## 방식 요약
- 원장 = Firebase Auth 이메일/비밀번호 계정 + **규칙 파일에 적힌 원장 UID 와 일치**. Firestore 의 `meta/directors` 같은 허용 목록 문서는 **쓰지 않는다**(만들 필요 없음).
- 그래서 이메일/비밀번호 로그인을 켜 두고 누가 계정을 만들어도(공개 웹 키로 가능) 그 계정은 원장이 되지 못한다.
- **원장을 바꾸거나 추가하려면 규칙 파일의 UID 를 고쳐 규칙을 다시 게시해야 한다.**
- Firebase 의 "가입 차단" 설정은 이 프로젝트에서 사용 가능한지 **확인되지 않았고**, 학생용 익명 로그인에 미치는 영향도 확인되지 않았다. **켜지 않는다.**

## 전환 순서 (한 단계씩)

각 단계 끝의 **확인**을 통과해야 다음으로 간다. 막히면 멈추고 알려 달라. 2~6단계는 같은 날 이어서 진행한다(보안 공백 시간을 줄이기 위해).

0. **PR #13 확인.** PR 댓글의 시험 결과가 모두 통과인지 확인한다(draft 상태, 병합하지 않은 상태).
1. **사전 준비(영향 없음).** 현재 Firestore 규칙 텍스트 전체를 복사해 파일로 저장한다(되돌리기용). 앱 안의 백업을 실행한다. 학생 접속이 적은 시간을 고른다. 학생에게 "앱을 닫았다가 다시 열어 주세요" 안내문을 준비한다.
2. **원장 계정 만들기.** Firebase 콘솔 → Authentication → Sign-in method 에서 **이메일/비밀번호** 사용 설정(익명은 그대로 켜 둠) → Users → 사용자 추가에서 원장용 이메일과 **새 비밀번호(12자 이상, 다른 곳에서 안 쓴 값)** 를 직접 입력한다. 지금 쓰는 `0000` 은 쓸 수 없다.
   - 확인: Users 목록에 **본인이 방금 만든 계정**(생성 시각 확인)이 있다. "이미 있는 이메일" 오류가 나면 중단하고 알려 준다(다른 사람이 선점했을 수 있음).
3. **앱 배포(별도 승인).** `index.html` 의 `DIRECTOR_AUTH` 를 `{ mode:'firebase', email:'<2단계 이메일>' }` 로 바꾼 버전을 개발 담당이 준비하고, 원장님이 승인한 뒤 배포한다. 이 시점에 규칙은 아직 옛 규칙이다.
   - 확인(새 브라우저/시크릿 창): 원장 모드에서 **2단계의 새 비밀번호**로 입장되고 옛 비밀번호 `0000` 은 거부된다. 학생 4자리 코드 입장·숙제 제출이 평소처럼 된다.
4. **UID 확인 → 규칙에 기재(아직 게시하지 않음).** 3단계에서 **로그인에 성공한 본인 계정**의 사용자 UID 를 콘솔 Users 에서 복사한다. `security/firestore.rules.phase1.proposed` 내용을 복사한 뒤 `REPLACE_WITH_DIRECTOR_UID` 를 그 UID 로 바꾼다(작은따옴표 안, 다른 부분은 그대로).
   - 확인: 규칙 텍스트에 `REPLACE_WITH_DIRECTOR_UID` 가 더 이상 남아 있지 않고, UID 가 Users 의 본인 계정 UID 와 한 글자도 다르지 않다.
5. **규칙 게시(원장님이 콘솔에서 직접, 4단계 직후).** Firestore → 규칙 탭에서 4단계 텍스트를 붙여넣고 게시한다. 직후 아래 "실기기 확인 목록" 을 진행한다.
6. **확인.** 원장 로그인·원장 화면 목록이 뜨고, 학생 코드 입장·숙제 제출·질문·사진이 되고, 시크릿 창에서 로딩이 끝까지 된다. Users 에 낯선 계정이 있어도 권한은 없지만, 정리를 위해 삭제해도 된다.
7. **관찰(며칠).** 빈 화면·"권한 없음" 증상이 없는지 본다. 있으면 화면·시각만 알려 달라(학생 이름·내용·비밀번호는 보내지 않는다).
8. **(별도 승인) 옛 비밀번호 삭제.** 7단계가 안정된 뒤에만 `meta/settings` 의 `adminPassword` 필드를 지운다. 옛 값은 이미 노출된 적이 있으므로 어디서도 재사용하지 않는다.

## 실패 시 되돌리기 — 규칙 먼저, 그다음 앱

| 증상 | 원인 후보 | 되돌리는 순서 |
|---|---|---|
| 5단계 직후 학생·원장 모두 이상 | 규칙 문제 | ① 콘솔 규칙 탭에서 **이전 규칙 게시**(1단계에서 저장한 텍스트 또는 규칙 기록의 이전 버전) |
| 원장만 로그인 거부("원장 권한이 없어요") | UID 오기재/오타 | 규칙의 UID 를 Users 의 UID 와 대조해 고쳐 **다시 게시**(학생은 영향 없음). 급하면 이전 규칙으로 되돌림 |
| 모두 무한 로딩 | 옛 앱 캐시 또는 규칙/앱 불일치 | 학생에게 앱 새로고침 안내. 계속되면 ① 규칙 되돌리기 |
| 규칙은 옛 규칙인데 원장 로그인 안 됨(3단계) | 이메일 오타·계정 미생성 | 앱을 `legacy` 판으로 재배포(규칙이 옛 규칙이라 안전) |
| 규칙을 되돌린 뒤에도 문제 | 앱 변경 | ② 앱을 `legacy` 판으로 재배포 |

**규칙이 새 상태일 때 앱만 `legacy` 로 되돌리면 로딩이 막힌다 → 항상 규칙을 먼저 되돌린다.**

## 실기기 확인 목록 (최소)
원장: ① 새 비밀번호 로그인·옛 비밀번호 거부 ② 학생·반 목록 ③ 숙제 승인/보완·코멘트 저장 ④ 새로고침 후 로그인 유지, 로그아웃 후 학생 모드 입장 ⑤ 전체 백업 ⑥ 월말 리포트 화면은 잠금 그대로(**초안 생성 버튼 누르지 않기**).
학생(폰 2종 이상): ⑦ 코드 입장·오늘 숙제 ⑧ **사진 첨부 숙제 제출**(외부 업로드 서버 포함)·원장 화면에서 사진 확인 ⑨ 질문(사진 포함)·답변 확인 ⑩ 공부 타이머·주말학습·STAD ⑪ 앱 재실행 후 로그인 유지, 옛 홈 화면 바로가기에서 무한 로딩이 없는지.
공통: ⑫ 시크릿 창에서 첫 화면 로딩 완료.
