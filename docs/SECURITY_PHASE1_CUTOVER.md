# 보안 1단계 — 운영 전환 절차 (원장용)

> 상태: **준비만 됨. 운영에는 아무것도 적용하지 않았다.** 아래는 원장님이 직접 승인하고 하나씩 진행하는 절차다.
> 비밀번호·API 비밀키는 개발 담당(Claude)에게 보내지 않는다. 비밀번호 입력은 원장님이 직접 한다. (원장 UID 는 비밀값이 아니라서 규칙 파일에 적어도 된다.)
> 판단 근거와 위험은 `SECURITY_PHASE1_DECISION_BRIEF.md` 참고.

## 방식 요약
- 원장 = Firebase Auth 이메일/비밀번호 계정 + **규칙 파일에 적힌 원장 UID 와 일치**. Firestore 의 `meta/directors` 같은 허용 목록 문서는 **쓰지 않는다**(만들 필요 없음).
- 그래서 이메일/비밀번호 로그인을 켜 두고 누가 계정을 만들어도(공개 웹 키로 가능) 그 계정은 원장이 되지 못한다.
- **원장을 바꾸거나 추가하려면 규칙 파일의 UID 를 고쳐 규칙을 다시 게시해야 한다.**
- Firebase 의 "가입 차단" 설정은 이 프로젝트에서 사용 가능한지 **확인되지 않았고**, 학생용 익명 로그인에 미치는 영향도 확인되지 않았다. **켜지 않는다.**

## 전환 순서 (한 단계씩)

각 단계 끝의 **확인**을 통과해야 다음으로 간다. 막히면 멈추고 알려 달라. 2~6단계는 같은 날 이어서 진행한다(보안 공백 시간을 줄이기 위해).

0. **PR #13 확인.** PR 댓글의 시험 결과가 모두 통과인지 확인한다(draft 상태, 병합하지 않은 상태).
1. **사전 준비(영향 없음).** 현재 Firestore 규칙 텍스트 전체를 복사해 파일로 저장한다(되돌리기용). 앱 안의 백업을 실행한다. 학생 접속이 적은 시간을 고른다. 학생에게 "앱을 닫았다가 다시 열어 주세요" 안내문을 준비한다.
2. **원장 계정 만들기.** Firebase 콘솔 → Authentication → Sign-in method 에서 **이메일/비밀번호** 사용 설정(익명은 그대로 켜 둠) → Users → 사용자 추가에서 원장용 이메일과 **새 비밀번호(12자 이상, 다른 곳에서 안 쓴 값)** 를 직접 입력한다. 지금 쓰는 `0000` 은 쓸 수 없다.
   - 확인: Users 목록에 **본인이 방금 만든 계정**(생성 시각 확인)이 있다. "이미 있는 이메일" 오류가 나면 중단하고 알려 준다(다른 사람이 선점했을 수 있음).
3. **앱 배포(별도 승인).** `index.html` 의 `DIRECTOR_AUTH` 를 `{ mode:'firebase', email:'<2단계 이메일>' }` 로 바꾼 버전을 개발 담당이 준비하고, 원장님이 승인한 뒤 배포한다. 이 시점에 규칙은 아직 옛 규칙이다.
   - 확인(새 브라우저/시크릿 창): 원장 모드에서 **2단계의 새 비밀번호**로 입장되고 옛 비밀번호 `0000` 은 거부된다. 학생 4자리 코드 입장·숙제 제출이 평소처럼 된다.
4. **UID 확인 → 규칙에 기재(아직 게시하지 않음).** 3단계에서 **로그인에 성공한 본인 계정**의 사용자 UID 를 콘솔 Users 에서 복사한다. `security/firestore.rules.phase1.proposed` 내용을 복사한 뒤 `REPLACE_WITH_DIRECTOR_UID` 를 그 UID 로 바꾼다(작은따옴표 안, 다른 부분은 그대로).
   - 확인: 규칙 텍스트에 `REPLACE_WITH_DIRECTOR_UID` 가 더 이상 남아 있지 않고, UID 가 Users 의 본인 계정 UID 와 한 글자도 다르지 않다.
5. **규칙 게시(원장님이 콘솔에서 직접, 4단계 직후).** Firestore → 규칙 탭에서 4단계 텍스트를 붙여넣고 게시한다. 직후 아래 "실기기 확인 목록" 을 진행한다.
6. **확인.** 원장 로그인·원장 화면 목록이 뜨고, 학생 코드 입장·숙제 제출·질문·사진이 되고, 시크릿 창에서 로딩이 끝까지 된다. Users 에 낯선 계정이 있어도 권한은 없지만, 정리를 위해 삭제해도 된다.
7. **관찰(며칠).** 빈 화면·"권한 없음" 증상이 없는지 본다. 있으면 화면·시각만 알려 달라(학생 이름·내용·비밀번호는 보내지 않는다).
8. **(별도 승인) 옛 비밀번호 삭제.** 7단계가 안정된 뒤에만 `meta/settings` 의 `adminPassword` 필드를 지운다. 옛 값은 이미 노출된 적이 있으므로 어디서도 재사용하지 않는다.

## 4단계 — UID 를 규칙에 적을 때 (오입력이 가장 흔한 사고)

적는 위치: 규칙 텍스트의 `function directorUids() { return ['REPLACE_WITH_DIRECTOR_UID']; }` — **작은따옴표 안의 글자만** 바꾼다. 여러 명이면 `['UID1', 'UID2']`.
- **게시 전 필수 대조**: 콘솔 Authentication → Users 에서 원장 계정 행의 이메일과 **사용자 UID** 를 나란히 보고, 복사한 값이 규칙 텍스트의 값과 한 글자도 다르지 않은지 두 번 확인한다. 앞뒤 공백·따옴표·줄바꿈이 섞이지 않게 한다.

| 입력 실수 | 게시 후 증상 | 학생 | 조치 |
|---|---|---|---|
| UID 오타·공백 포함·잘림(존재하지 않는 값) | 원장 모드에서 올바른 비밀번호를 넣어도 **"이 계정에는 원장 권한이 없어요."** 가 뜨고 입장되지 않음(곧바로 학생용 익명 세션으로 돌아감). 이미 열려 있던 원장 화면은 목록이 비거나 저장이 실패하고 "연결 끊김" 표시, 새로고침하면 "원장 권한을 확인하지 못해 로그아웃했어요." | **영향 없음** | 규칙의 UID 를 고쳐 **다시 게시**(학생이 정상이므로 규칙을 옛 규칙으로 되돌리는 것보다 UID 수정이 우선 — 되돌리면 다시 전부 열린 상태가 된다) |
| **다른 사람 계정**의 UID 를 넣음 | 원장은 못 들어가고, 그 계정이 원장 권한을 가짐 | 영향 없음 | 즉시 올바른 UID 로 수정·재게시(그 사이 노출 최소화를 위해 같은 날 바로) |
| 자리표시자 `REPLACE_WITH_DIRECTOR_UID` 를 그대로 게시 | 위 첫 줄과 같음(아무도 원장이 아님) | 영향 없음 | UID 기재 후 재게시 |
| 따옴표·쉼표·괄호를 지움(문법 오류) | 콘솔 규칙 편집기가 게시를 막고 오류를 표시하는 것으로 알려져 있으나 **이 프로젝트에서 확인되지 않음.** 게시가 거부되면 기존 규칙이 유지됨 | 변화 없음 | 텍스트를 저장해 둔 원본으로 다시 시작 |

**규칙을 안전하게 되돌리는 방법**
1. (기본) **1단계에서 저장해 둔 이전 규칙 텍스트 전체**를 규칙 탭에 붙여넣고 게시한다. 그래서 1단계 저장이 필수다.
2. (보조) 콘솔의 규칙 게시 기록에서 이전 버전을 선택해 게시한다(기록 화면이 보이는지는 이 프로젝트에서 확인되지 않음 — 1번을 기본으로 한다).
3. 되돌리면 **현재와 같은 전부 열린 상태로 돌아간다**(보안 개선 없음). 그래서 증상이 원장 로그인에만 있고 학생이 정상이라면 되돌리기보다 UID 를 고쳐 재게시한다.
4. 규칙이 새 상태일 때 앱만 `legacy` 로 되돌리면 로딩이 막힌다 → **항상 규칙을 먼저, 앱은 그다음.**

## 규칙 게시 후, 옛 앱 화면을 쓰는 학생

- **무엇이 보이나**: 옛 버전 `index.html` 은 시작할 때 `meta/settings` 를 읽는다. 새 규칙이 이를 막으면 12초 뒤 **"서버 연결이 너무 오래 걸리고 있어요…" 오류 화면과 [다시 시도] 버튼**이 뜬다(코드의 안전장치, 영구 로딩은 아님). 이미 앱을 열어 두고 쓰던 학생은 화면이 그대로 있다가 "연결 끊김 - 재시도 중"이 뜨거나 일부 데이터가 갱신되지 않을 수 있다.
- **[다시 시도]가 해결 못 하는 경우**: 버튼은 페이지를 다시 불러오는데, 브라우저가 **옛 `index.html` 을 캐시에서 그대로 쓰면** 같은 오류가 반복된다. GitHub Pages 의 캐시 시간은 일반적으로 10분 안팎이지만 **이 사이트에서 확인되지 않음**.
- **확인된 코드 사실**: `index.html` 에는 서비스워커나 웹앱 매니페스트가 없다. 홈 화면 바로가기는 일반 웹 주소 바로가기로 보이며, 마지막 화면이 메모리에 남아 있는 경우(앱 전환 화면에서 되돌아옴)가 문제다. 다른 HTML 파일(`batch.html` 등)은 확인하지 않았다.
- **학생 안내문(복사해서 사용)**: "앱이 멈추거나 '서버 연결' 오류가 보이면, 화면을 완전히 닫았다가(최근 앱 목록에서 밀어서 종료) 다시 열어 주세요. 그래도 안 되면 브라우저의 '새로고침'을 눌러 주세요. 바로가기로 열었다면 바로가기를 닫고 다시 여세요."
- **원장 기기**: 옛 원장 로그인 상태(`legacy`)로 열려 있던 화면은 규칙 게시 후 **저장이 실패**한다. 새로고침 후 새 비밀번호로 다시 로그인한다.
- **언제 안내하나**: 3단계(앱 배포) 직후와 5단계(규칙 게시) 직전에 한 번씩. 배포 후 10~15분이 지난 뒤 게시하면 대부분의 기기가 새 앱을 받은 상태가 되지만, 이 시간이 충분한지는 **확인되지 않음**.

## 실패 시 되돌리기 — 규칙 먼저, 그다음 앱

| 증상 | 원인 후보 | 되돌리는 순서 |
|---|---|---|
| 5단계 직후 학생·원장 모두 이상 | 규칙 문제 | ① 저장한 이전 규칙 텍스트 게시 |
| 원장만 로그인 거부 | UID 오입력(위 표) | 규칙의 UID 수정 후 재게시 |
| 일부 학생만 오류 화면 | 옛 앱 캐시 | 학생 안내문대로 완전 종료 후 재실행. 다수면 ① |
| 규칙은 옛 규칙인데 원장 로그인 안 됨(3단계) | 이메일 오타·계정 미생성 | 앱을 `legacy` 판으로 재배포(규칙이 옛 규칙이라 안전) |
| 규칙을 되돌린 뒤에도 문제 | 앱 변경 | ② 앱을 `legacy` 판으로 재배포 |

## 외부 업로드(사진) 경로 — **운영 서버에서 검증되지 않음**

- 사진 숙제 제출·질문 사진·해설 사진·PDF 문제 분석은 앱이 외부 서버(`mnm-photo-api.jihagondu.workers.dev`)에 Firebase 로그인 토큰을 보내 저장·삭제한다. 이 서버의 코드는 **이 저장소에 없어서** 토큰을 어떻게 검증하는지, 어떤 로그인 종류를 받는지 **확인할 수 없다**.
- 앱은 요청에 `X-MNM-Role` 헤더(학생/원장 구분)를 **스스로 적어 보낸다.** 서버가 이 값을 믿는다면 누구나 원장이라고 적어 보낼 수 있다 — **확인되지 않음, 이번 PR 의 범위 밖**(문제저장소 작업에서 점검).
- 1단계로 바뀌는 것: 원장이 보내는 토큰이 익명 로그인 토큰에서 이메일/비밀번호 로그인 토큰으로 바뀐다. 서버가 익명 토큰만 허용하도록 만들어져 있다면 **원장의 사진 업로드·삭제·PDF 분석이 실패**할 수 있다. 학생 토큰은 그대로(익명)다.
- 에뮬레이터 시험에는 이 서버가 포함되지 않았다(사진은 시험에서 첨부 없이 제출). **앱 배포 후 규칙 게시 전에 반드시 실기기로 확인**한다: 학생 사진 숙제 제출, 학생 질문 사진, 원장 해설 사진, 원장 사진 삭제.
