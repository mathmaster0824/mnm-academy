# 보안 개선 계획서 — 전체 컬렉션 · 인증 · 데이터 구조 (2026-10-20, 초안)

> **상태: 계획과 테스트 준비만 했다.** Firestore 규칙 배포, main 병합, 서비스 배포, 운영 데이터 열람·변경·삭제는 하지 않았다.
> 초안 규칙은 GitHub Actions 의 Firestore Emulator 에서 **가짜 데이터로 실행해 308개 테스트가 모두 통과**했다(§9, 커밋 cc50d1a 기준).
> 그러나 **운영 Firebase 에는 어떤 것도 적용·실행하지 않았고**, 앱 화면 전체를 규칙에 붙여 본 시험은 아직 없다(§8.3, §9).

## 0. 한눈에 보기

| 문제 | 근거 | 이 계획의 해결 단계 |
|---|---|---|
| 로그인한 세션은 **모든 컬렉션을 읽고·쓰고·지울 수 있다** (학생 앱은 익명 로그인) | 콘솔 규칙 탭 확인(2026-10-19): `match /{document=**} { allow read, write: if request.auth != null; }` | 1단계(원장 영역·상태값) + 2단계(학생 간 격리) |
| **원장 비밀번호**가 모든 접속자 브라우저에 읽히고, **덮어쓸 수도 있다** | `attachCoreListeners` 가 로그인 전에 `meta/settings` 구독, `tryDirectorLogin` 이 브라우저에서 비교 | 1단계 (서버가 검증하는 원장 로그인) |
| 모든 학생의 **로그인 코드(4자리)** 가 모든 접속자에게 읽힌다 → 학생 사칭 가능 | `students` 전체 구독 + `tryStudentLogin` 이 브라우저에서 코드 비교 | 2단계 (서버가 코드 검증) |
| 같은 반 학생들의 점수·메모가 **한 문서**에 들어 있어 학생별 권한을 줄 수 없다 | `classRecords/{반}_{날짜}` = `{학생ID: {...}}` | 2단계 (학생별 사본) |
| 월말 리포트가 열린 규칙 아래에 놓인다 | PR #11 (보류) | 1단계 규칙이 근본 해결, PR #11 은 임시 |

**원장 비밀번호를 새 값으로 바꾸는 것만으로는 해결되지 않는다.** 새 값도 같은 문서에 같은 방식으로 저장되어 접속자가 읽을 수 있다. 서버가 검증하는 원장 로그인이 필요하다(§4).

**학생별 권한을 판단하려면 인증 변경과 데이터 구조 변경이 모두 필요하다.** 지금 학생 세션은 "누구인지" 서버가 알 수 없고(익명), 반 단위 문서는 여러 학생 데이터를 함께 담고 있다(§4, §5).

## 1. 확인한 사실과 확인하지 못한 것

**확인(코드 또는 콘솔 화면):**
- 배포된 규칙 전문(위 인용). 마지막 게시 2026-08-19 15:59, 직전 버전 14:43(내용 미확인). 만료일 없음.
- 앱은 `fauth.signInAnonymously()` 로 접속한다(`initFirebase`). 익명 로그인은 켜져 있다고 본다(앱이 동작하므로).
- 원장 로그인: `if(v === db.settings.adminPassword)`. 없으면 기본 `0000` 문서를 생성하는 코드가 있다(`attachCoreListeners`).
- 학생 로그인: `db.students.find(s => String(s.code) === 입력값)`. 학생 코드는 `students` 문서의 필드.
- 최상위 `monthlyReports` 컬렉션 없음(원장이 콘솔 목록에서 확인).
- 사진은 Firestore 문서 안 base64(레거시) 또는 외부 Worker(`mnm-photo-api.jihagondu.workers.dev`, R2) 참조. Firebase Storage SDK 는 쓰지 않는다.

**확인하지 못한 것(§10 에 정리):** Authentication 설정 전체, API 키 제한 여부, App Check 설정(콘솔에 "앱 체크 구성" 안내가 보임 → 미구성으로 추정), 사진 Worker 의 토큰 검증 방식(코드가 저장소에 없음), 운영 데이터의 ID 형식·필드 누락 여부, 학생 화면이 다른 학생 정보를 쓰는지 여부.

## 4. 인증 설계

### 4.1 원장 — 서버가 검증하는 방식 (1단계)
**권고:** Firebase Authentication **이메일/비밀번호 계정 1개**(원장) + **원장 UID 를 Firestore 규칙 파일에 직접 기재**(Firestore 문서 허용 목록은 쓰지 않음 — 공개 클라이언트가 수정할 수 있어 권한 탈취 경로가 되기 때문, §13 참고).
- 비밀번호는 Firebase 서버가 검증한다. 앱은 지금처럼 **비밀번호 한 칸**만 보여 주고 이메일은 앱 안에 고정한다(원장 사용 흐름 유지).
- 규칙: `sign_in_provider == 'password'` 이면서 `request.auth.uid` 가 **규칙 파일에 적힌 원장 UID** 와 같아야 원장. 익명·위조 claim 은 통과하지 못한다(테스트 포함).
- 허용 목록 문서는 쓰지 않는다(§13-1). **게시 전 1회** 콘솔에서 원장이 자기 UID 를 규칙 텍스트에 직접 적는다(코드 실행 불필요).
- 영향: 비밀번호는 **6자 이상**이어야 한다(현재 기본값 `0000` 불가). 비밀번호 변경은 Firebase 방식(`updatePassword`)으로 바뀐다. 분실 시 콘솔에서 재설정. 원장 로그아웃 후 학생 화면용 익명 세션을 다시 만든다.
- 이 방식은 **Cloud Functions 가 필요 없다.**

**대안 비교**
| 방식 | 장점 | 단점 | 판단 |
|---|---|---|---|
| 이메일/비밀번호 + 규칙에 UID 직접 기재 | 코드 실행 없이 시작, Functions 불필요, 변조 경로 없음 | 원장 변경 시 규칙 재게시 필요 | **채택(§13-1)** |
| 이메일/비밀번호 + 허용 목록 문서 | 코드 실행 없이 시작 | 옛 규칙 구간에서 누구나 문서 수정 가능 → 권한 탈취 경로 | **폐기** |
| Admin SDK 로 `mnmDirector` custom claim 부여 | 규칙이 단순, 추가 읽기 없음 | 개발자가 서비스 계정으로 스크립트를 한 번 실행해야 함 | 2단계에서 전환 가능 |
| Cloud Functions 가 비밀번호를 받아 custom token 발급 | 로그인 UX 를 지금과 거의 동일하게 유지 | 비밀번호 저장·시도 제한을 직접 구현해야 함 | 비권고 |
| 비밀번호만 바꾸기 | 즉시 가능 | **노출 구조가 그대로** | 해결 아님 |

### 4.2 학생 — 서버가 "누구인지" 알게 하는 방식 (2단계)
**왜 필요한가:** 학생이 다른 학생의 자료를 못 보게 하려면 규칙이 "이 세션은 학생 A"라는 사실을 알아야 한다. 익명 세션은 그 정보가 없다. 클라이언트가 보내는 값(`studentId` 필드, `session.mode`)은 서버가 신뢰할 수 없다.

**권고:** Cloud Functions `studentLogin`(호출 가능 함수)이 학생 코드를 **서버에서** 확인하고 성공하면 custom token(claim: `role='student'`, `studentId`)을 발급한다.
- 효과: 학생 화면 사용법은 그대로(코드 4자리 입력). 코드는 더 이상 클라이언트로 내려가지 않는다 → `students` 전체 목록 읽기 폐지.
- **4자리 숫자 코드는 전수 대입(1만 가지)에 약하다.** 서버에서 시도 횟수 제한·지연이 필수이고, 코드 길이 확대나 학생 선택 추가를 원장이 결정해야 한다(§11).
- 필요한 것: Blaze 요금제(현재 체험판 사용 중, 콘솔 화면 기준 48일·₩408,763 남음 — 체험 종료 후 비용은 무료 한도 내라면 거의 0 으로 **예상**하나 미확인), Functions 배포, 서비스 계정 권한.
- 대안(학생별 Firebase 계정)은 4자리 코드를 비밀번호로 쓸 수 없고(최소 6자) 계정 관리가 늘어 비권고.

**App Check** 는 사이트 밖에서 오는 요청을 줄이는 보조 수단이다. 로그인 방식이나 규칙을 대체하지 못한다. 기존 기기 영향 때문에 별도 단계에서 검토한다.

## 5. 데이터 구조 변경이 필요한가? — **필요하다**

| # | 변경 | 이유 | 데이터 변경 성격 |
|---|---|---|---|
| D1 | 학생 코드 `students.code` 를 서버 전용 위치로 | 모든 접속자가 읽는 문서에 들어 있음 | 이동(기존 필드 삭제는 별도 승인) |
| D2 | `students` 의 원장 메모·경고·성실도 분리 여부 결정 | 학생 본인 문서를 읽게 하면 같이 보임 | 결정 후 추가 문서로 분리 |
| D3 | `classRecords`·`weeklyPlans`·`fridaySupp` → 학생별 사본 `studentRecords`·`studentPlans`·`studentFridaySupp` | 한 문서에 반 전체가 들어 있어 학생별 규칙이 불가 | **추가** 컬렉션(원본 유지). 서버 트리거가 생성, 기존 데이터는 백필 |
| D4 | 학생 앱의 문서 ID 범위 쿼리를 "내 문서 정확 조회"로 | 규칙은 ID 범위 쿼리를 증명하지 못해 `list` 를 허용할 수 없음 | **앱 코드만** (데이터 변경 없음) |
| D5 | `classes.studentIds` 와 레거시 `students.classId` 정합성 | 규칙은 `studentIds` 로 소속을 판단. `classId` 만 있고 `studentIds` 에 없는 학생은 반을 읽지 못함 | 점검 후 필요시 추가 |
| D6 | `kmm`·`schoolScores`·`questions`·`answerSubmissions` 의 `studentId` 필드 누락 문서 | 규칙이 `studentId` 필드로 판단 | 점검 후 필요시 백필 |
| D7 | 학생 ID 형식 가정 검증 | 접두어 규칙이 'stu_'+10자 고정 길이를 가정(다른 ID 의 접두어가 되지 않음) | 읽기 점검 |
| D8 | 질문→문제저장소 연결을 서버로 이전 | 학생 세션이 `problems*` 에 직접 쓰고 있음 | 문제저장소 작업과 함께 |

모든 변경은 **추가·병행 방식**이고, 기존 필드·문서를 삭제하거나 덮어쓰는 단계는 각각 원장 승인을 받는다.

## 6. 문제저장소 영역 (이번 범위 밖)
- 문제저장소 코드는 이번 작업에서 건드리지 않았다. 규칙 초안에서도 `problems`, `problemKeys`, `problemDrafts`, `problemSources` 는 **1단계에서 현행 유지(로그인 전체 허용)** 로 두었다. 이유: 학생이 질문을 올리면 학생 세션이 이 컬렉션에 쓰기 때문에, 닫으면 질문→저장소 연결이 조용히 실패한다(오류가 `catch` 로 삼켜짐).
- 따라서 **정답키(`problemKeys`)가 1단계 이후에도 로그인 세션에 읽힌다.** 이 노출은 D8(서버 이전)로 닫는다. 문제저장소 작업의 선행 항목이다.
- 2단계 규칙 초안은 이 네 컬렉션을 원장 전용으로 닫는다(D8 이후에만 배포 가능).

## 7. 단계별 이행 계획

각 단계는 **원장 승인 → 에뮬레이터 통과 → 배포 → 점검표 확인** 순서다. 어느 단계든 규칙은 이전 버전(현재 규칙은 `security/firestore.rules.current`)으로 되돌릴 수 있다.

**0단계 — 지금(승인된 범위)**: 계획서·테스트·CI 준비. 월말 초안 버튼 사용 중지, PR #11 보류.

**1단계 — 원장 서버 인증 + 원장 영역 보호**
1. 앱 변경(하위 호환): ① 원장 Firebase 로그인 ② 앱 로딩이 `meta/settings` 에 의존하지 않게 변경 ③ 기본 비밀번호(`0000`) 문서 생성 코드 제거 ④ 원장 세션 복원을 Firebase 세션 기준으로 변경 ⑤ 학생 화면은 익명 세션에서 `meta` 를 읽지 않게.
2. 원장이 콘솔에서: 이메일/비밀번호 로그인 켜기 → 원장 계정 만들기 → 사용자 UID 확인(규칙 파일에 적을 값, 안내서 제공). *설정·문서 생성은 운영 변경이라 그때 별도 승인.*
3. 새 앱 버전 배포 → 원장 로그인 확인 → (캐시 때문에 구 버전을 쓰는 기기가 사라질 때까지 대기).
4. 에뮬레이터 통과 후 **1단계 규칙 배포**. 직후 점검표(§8.4)로 학생 로그인·숙제 제출·질문·STAD·주말학습, 원장 기능 확인. 이상 시 즉시 규칙 롤백.
5. `meta/settings.adminPassword` 필드 삭제는 **별도 승인**(데이터 변경).
- **위험:** 구 버전 앱이 열려 있는 기기는 `meta/settings` 읽기가 거부돼 로딩 오류 화면이 뜬다. 앱 버전 확인·새로고침 안내와 학생이 적은 시간대 배포로 완화(구 버전 비율을 측정할 방법은 현재 없음 — 미확인).
- 1단계가 **못 막는 것**: 학생 A 가 B 의 자료를 읽거나 B 이름으로 쓰는 것, 학생 코드 노출(§0). 테스트 `phase1.test.js` ⑥ 이 이 한계를 그대로 고정한다.

**2단계 — 학생별 권한**
1. 서버: `studentLogin`, 학생별 사본 트리거 + 백필, 질문→저장소 연결 서버화.
2. 앱: 학생 로그인을 custom token 으로, 범위 쿼리를 정확 조회로, 사본 컬렉션 읽기.
3. 점검: D5~D7 읽기 점검 → 필요 시 백필(승인).
4. 에뮬레이터 + (권고) 앱 화면 시험을 에뮬레이터에 연결해 거부 지점 확인 → 2단계 규칙 배포 → 익명 로그인 중단 → 문제저장소 컬렉션 폐쇄.

**3단계 — 마무리**: custom claim 전환 검토, App Check 검토, 사진 Worker 인증 점검, 정기 점검.

## 9. 실행 결과와 남은 한계 (정직한 상태)

**실행 환경:** 이 개발 환경에서는 에뮬레이터 실행 파일을 받을 수 없어(정책상 403) 직접 실행하지 못했다. 대신 PR #12 의 GitHub Actions(공개 러너, 가짜 프로젝트 `demo-*`, 가짜 데이터)가 같은 테스트를 에뮬레이터에서 실행했다. 운영 프로젝트에는 접속하지 않았다.

**결과 (커밋 cc50d1a):** 기준선·1단계·2단계 **308/308 통과**, PR #11 제안안(월말 리포트 잠금) **34/34 통과**. 규칙 파일 3개가 에뮬레이터에서 컴파일됐다.

**실행으로 알게 된 것**
- 첫 실행에서 테스트 설계 오류 1건(파일 간 프로젝트 ID 공유로 규칙이 뒤섞임)을 고쳤다.
- 두 번째 실행에서 **규칙의 실제 구멍 1건**을 발견했다: 학생 세션이 숙제 상태를 '제출완료'로 둔 채 `teacherComment` 를 새로 쓸 수 있었다. 앱의 재제출 동작(코멘트를 없애거나 그대로 두기)을 보존하면서 새 값만 막도록 고쳤다(양 단계, 테스트 3건 추가). 이후 308/308.
- 확정된 것: `array-contains`·`studentId` 쿼리가 규칙으로 허용됨, 인증 공급자(`sign_in_provider`)·custom claim 위조 차단, 문서 ID 접두어·접미어 규칙, 접두어 충돌 차단.

**여전히 확인하지 못한 것**
- 통과는 "내가 쓴 시나리오"에 대한 결과다. **실제 앱 코드가 하는 읽기·쓰기를 전부 덮는지는 별개**다(코드 정독 기반). 앱 화면 시험을 에뮬레이터에 연결해 거부 지점을 잡아야 한다(§8.3).
- 1단계 규칙의 알려진 한계(학생 A→B 접근 등)는 의도대로 열려 있고 테스트가 그렇게 고정한다. 학생 세션이 `reviewCount`·`reviewReason`·`reviewedAt` 값을 조작하는 것은 규칙만으로 막지 못한다(앱이 값을 정해 보냄).
- 이메일/비밀번호 로그인의 시도 제한은 **미확인**(규칙은 더 이상 문서를 `get()` 으로 읽지 않아 그 비용·한도 문제는 사라짐).
- 운영 데이터 형식(§10 4번)과 사진 Worker 인증(§10 3번)은 미확인.
- 규칙·앱·서버 변경은 **하나도 운영에 적용하지 않았다.**

9. 이메일/비밀번호 로그인의 시도 제한 수치.

## 11. 원장이 결정할 것
1. 1단계 진행 승인(앱 변경 + 콘솔에서 원장 계정 만들기, 규칙에 원장 UID 기재).
2. 원장 비밀번호를 **6자 이상**으로 정하기, 분실 시 재설정에 쓸 이메일.
3. 학생에게 보여도 되는 반 기록 필드(출결·점수·메모·수업상세 중 무엇).
4. 학생 코드 방식: 4자리 유지(시도 제한으로 보완) vs 강화.
5. 운영 데이터 읽기 점검(D5~D7)과 백필의 승인 시점.

### 13-1. 원장 판정 방식 변경 (허용 목록 문서 → 규칙에 UID 직접 기재)
- 이유: 현재 규칙(`request.auth != null`)에서는 로그인한 누구나 `meta/directors` 를 수정할 수 있고, 이메일/비밀번호 로그인이 켜지면 공개 웹 키로 누구나 계정을 만들 수 있다. 규칙 배포 전에 공격자가 자기 UID 를 목록에 넣으면 배포 뒤 원장 권한이 된다. 배포 전후 목록 확인은 탐지일 뿐 예방이 아니다.
- 변경: 규칙 `isDirector()` = 비밀번호 로그인 **그리고** `request.auth.uid in directorUids()`(규칙 파일에 적은 UID). 저장소에는 자리표시자 `REPLACE_WITH_DIRECTOR_UID` 만 있고, 게시 때 원장님이 콘솔에서 확인한 UID 로 바꿔 게시한다. UID 는 비밀값이 아니다. 자리표시자 그대로 게시하면 아무도 원장이 되지 못한다(학생 기능은 유지).
- 앱: 원장 확인은 "원장 전용 경로(`meta/_directorCheck`)를 서버에서 읽어 보기"로 판정(화면 안내용, 실제 권한은 서버 규칙).
- 원장 변경·추가는 규칙 수정 후 **재게시**가 필요하다.
- 가입 차단 설정(Identity Platform "Enable create (sign-up)")은 이 프로젝트에서 사용 가능한지 **확인되지 않았고**, 익명 로그인에 미치는 영향도 확인되지 않아 사용하지 않는다.
